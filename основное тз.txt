Функциональные требования
Эти требования описывают принцип работы интернет-магазина, учитывайте их в своём проекте.
Главная страница:
содержит каталог товаров;
при нажатии на карточку товара открывается модальное окно с информацией о товаре;
при нажатии на иконку корзины открывается корзина;
на иконке корзины отображается счётчик — он показывает количество товаров в корзине.
Просмотр товара:
показана детальная информация о товаре;
присутствует кнопка «Купить», если товар не был выбран покупателем;
при нажатии на кнопку «Купить» товар добавляется в корзину (если не был добавлен в корзину ранее);
если товар находится в корзине, кнопка должна быть заменена на «Удалить из корзины»;
при нажатии на кнопку «Удалить из корзины» товар удаляется из корзины;
после нажатия кнопки модальное окно закрывается;
если у товара нет цены, кнопка в карточке должна быть заблокирована и иметь название «Недоступно».
Корзина:
отображается список товаров, которые выбрал покупатель;
для каждого товара указана цена и присутствует кнопка удаления. Если нажать на кнопку, товар удаляется из корзины;
отображается общая стоимость товаров в корзине;
присутствует кнопка оформления покупки;
если в корзине нет товаров, кнопка оформления должна быть деактивирована;
если товаров нет в корзине — вместо списка товаров выводится надпись «Корзина пуста»;
при нажатии на кнопку «Оформить» открывается модальное окно с формой оформления товара.
Оформление товара:
Первый шаг:
выбор способа оплаты;
ввод адреса доставки;
если адрес доставки не введён, появляется сообщение об ошибке;
если способ оплаты не выбран, появляется сообщение об ошибке;
кнопка «Далее» может быть активной, если: на форме нет ошибок, выбран способ оплаты и поле адреса доставки непустое;
при нажатии «Далее» открывается вторая форма оформления покупки.
Второй шаг:
ввод почты и телефона покупателя;
если одно из полей не заполнено, появляется сообщение об ошибке;
кнопка «Оплатить» может быть активной, только если на форме нет ошибок и поля почты и телефона непустые;
при нажатии на кнопку оплаты выполняется передача данных о заказе на сервер, появляется сообщение об успешной оплате, товары удаляются из корзины, данные покупателя очищаются.
Требования ко всем страницам:
Модальные окна закрываются:
по клику вне модального окна;
по клику на иконку «Закрыть» (крестик).
Модальные окна не должны скролиться.

Написать документацию классов слоя Представления (View). Опишите все классы, которые необходимы для отображения сайта. Для этого обратите внимание на макет и вёрстку сайта и следуйте инструкциям из видеоразбора.
Основные моменты:
каждый класс представления отвечает за свой блок разметки;
три класса для работы с тремя разными темплейтами карточки должны иметь одного родителя. В родительский класс должен быть вынесен общий для всех дочерних классов функционал;
два класса для форм должны иметь одного общего родителя, в который выносится общий для всех форм функционал;
модальное окно не может иметь дочерних классов, от него не могут наследоваться другие классы. Вся разметка, которая отображается в модальных окнах, — это самостоятельные компоненты. Они могут быть выведены в любой блок сайта, в том числе и в модальном окне;
в ответ на любое действие пользователя должно генерироваться событие, которое будет обработано Презентером.

Реализовать классы представления в коде. Создайте необходимые файлы с кодом классов представления. После этого всегда старайтесь тестировать работу класса.
Основные правила, которые вам стоит учитывать при написании кода:
элементы разметки должны быть найдены в конструкторе класса и сохранены в полях класса. Это касается всех элементов, за которые отвечает класс и с которыми предполагается взаимодействие.
класс представления не хранит в полях никаких данных — за хранение данных отвечает только Модель данных;
все слушатели событий устанавливаются один раз в конструкторе класса;
метод render() класса, вызываемый без передачи аргументов, должен возвращать разметку класса;
классы представления не должны содержать логику. А ещё они не могут самостоятельно принимать решение о том, как изменится их разметка из-за действий пользователя;
о действиях пользователя класс представления уведомляет с помощью брокера событий или вызывает обработчик, полученный в конструкторе. В случае, если в класс представления передается обработчик, то этот обработчик должен содержать генерацию события с помощью брокера событий;
класс представления не должен содержать геттеров или методов get… для получения из представления данных, все данные в приложении хранятся только в Моделях данных.
Обратите внимание:
в компоненте модального окна, для включения и выключения видимости модального окна используется модификатор 'modal_active', который добавляется элементу с классом "modal"
в компонентах карточек товара, для корректного отображения фона категорий товара используются модификаторы элемента с классом 'card__category'. Используйте объект categoryMap из файла src/utils/constants.ts
в компоненте формы с выбором оплаты используется модификатор 'button_alt-active' для выделения кнопки с выбранным видом оплаты.
Создайте ещё один раздел в документации — в нём будет описание событий, которые генерируются в приложении. Каждый раз, когда вы прописываете в классе генерацию какого-то события, записывайте его в этот раздел вместе с описанием события.
Помните: при обработке действий пользователя в классе может быть не только сгенерировано событие. Ещё в классе может быть вызван обработчик, который класс получил в конструкторе при создании его экземпляра.

События в Модели данных. Доработайте модели данных — необходимо сохранить всю структуру и методы. В методы, в которых происходит сохранение данных, добавьте генерацию событий. Любое изменение данных в модели должно эмитить событие.

Презентер. Вот вы и дошли до самого главного шага. У вас готовы все инструменты, вы убедились, что каждый компонент может работать независимо от других. Пора добавить в проект логики.
Первое, что вам нужно сделать, — это добавить в документацию раздел «Презентер». В нём будет описание последнего слоя вашего приложения. Так как у приложения только одна страница, достаточно одного презентера, который будет отвечать за логику работы этой страницы. Выносить код «Презентера» в отдельный класс необязательно — пишите код в основном скрипте приложения main.ts.
Если вы чувствуете в себе силы и готовы выполнить более сложное задание, то можете реализовать «Презентер» в отдельном классе. Не забывайте, что при таком выборе не должно быть нарушений паттерна MVP и принципов ООП. Используйте инверсию зависимостей и избегайте высокой связанности между компонентами.
О выбранном вами подходе напишите в разделе «презентер» вашей документации.
Перед написанием кода презентера следует удалить код, написанный для тестирования компонентов. Оставьте только код запроса к серверу за массивом товаров и сохранение этих товаров в модели данных.
Код презентера, по сути, состоит из обработчиков событий. Каждое событие должно быть обработано, а действия с данными или отображением должны быть выполнены согласно логике приложения.
Помните: если вы вызвали метод для сохранения данных, это не повод тут же вызывать ререндер компонента представления. Представление должно перерисовываться только в двух случаях:
при обработке события от модели данных, говорящего о том, что данные изменились;
или в результате обработки события открытия модального окна.
В вашем «Презентере» не должно быть генерации событий. Презентер обрабатывает события, а не генерирует их.
Начните с главной страницы. В модели данных, которая отвечает за хранение массива с товарами в каталоге, у вас есть метод. Этот метод сохраняет полный массив товаров, и в нём вы ранее должны были сгенерировать событие. Пришло время это событие обработать.
В Презентере (main.ts) установите слушатель этого события.
Напишите обработчик. Используя метод модели данных, он получит массив товаров.
Для каждого элемента массива нужно создать разметку карточки. Для этого используйте класс представления, который отвечает за карточку для каталога.
Соберите все разметки в один массив. Затем передайте его в рендер компонента, который отвечает за каталог на главной странице.
Если всё сделано правильно, то на странице приложения вы должны увидеть полный каталог товаров.
Напишите код обрабатывающий все остальные события, которые вы генерировали в моделях данных и представлениях.
Какие события должны быть в приложении Веб-Ларёк (сверьте свой список с приведенным ниже):
В Моделях данных:
изменение каталога товаров
изменение выбранного для просмотра товара
изменение содержимого корзины
изменение данных покупателя
В Представлениях:
выбор карточки для просмотра
нажатие кнопки покупки товара
нажатие кнопки удаления товара из корзины
нажатие кнопки открытия корзины
нажатие кнопки оформления заказа
нажатие кнопки перехода ко второй форме оформления заказа
нажатие кнопки оплаты/завершения оформления заказа
изменение данных в формах
Если в вашем приложении генерируются дополнительные события, они также должны быть обработаны.
Не пытайтесь написать весь код сразу — постепенно реализуйте действие за действием и по ходу дела проверяйте, как всё работает в интерфейсе.

Требования к документации
В файле README.md в корне проекта приведено краткое описание проекта, инструкция по его запуску и документация на проект.
Документация должна содержать:
описание структуры базового кода, компонентов и моделей данных, из которых состоит приложение, и назначения каждого элемента;
описание программного интерфейса компонентов и назначение каждой его части;
для каждого класса должны быть описаны: назначение класса, конструктор, поля и методы с указанием типов данных, которые хранятся или используются, как параметры или возвращаемые из методов значения;
описание типов данных, с которыми работает приложение;
описание архитектурного паттерна  MVP.
Если проект содержит UML-схему структуры классов, то она в формате JPEG или PNG.
Исходный код проекта соответствует приведённой документации. Если в код проекта вносятся изменения, они отражены в документации.
Требования к архитектуре проекта
Понятная структура классов. Каждый класс имеет одно предназначение и не перегружен функционально.
Базовый код отображения выделен, нет дублирования кода по унаследованным блокам.
Нет дублирования данных, хранимых в разных классах отвечающих за работу с данными.
Все взаимодействия с интерфейсом производятся с использованием классов, отвечающих за отображение.
Все DOM-элементы, с которыми взаимодействует класс, сохранены в поля класса; их повторный поиск не производится или закэширован.
Все DOM-элементы, с которыми взаимодействует класс являются дочерними основному элементу разметки, за который отвечает класс.
Взаимодействие между классами реализуется вне самих классов, например через события или через передачу экземпляров этих классов.
Повторяющиеся части кода выделены в утилиты в виде функций или вспомогательных классов.
Запросы к API не интегрированы напрямую в компоненты отображения или модели данных.
Класс для работы с сервером должен использовать функционал класса Api через композицию или наследование.
Стиль написания кода
Форматирование кода:

код проекта отформатирован единообразно,
нет нарушений иерархии отступов.
Объявление переменных:
для объявления переменных используется let и const, не используется объявление через var;
если переменная не перезаписывает своё значение, она объявлена через const;
нет «магических значений», все константные значения записаны в переменные.
Именование переменных:
имена переменных и функций написаны в стиле camelCase;
имена переменных — существительные, отражающие то, что в них хранится;
если в проекте есть несколько переменных с похожими данными, по их наименованиям понятно, что хранится в каждой переменной;
имена классов и типов данных написаны в стиле PascalCase;
имена массивов — существительные во множественном числе;
имена функций начинаются с глагола, отражающего то, что они делают;
для именования не используется транслит и неуместные сокращения.
Требования к типизации проекта
Код типов должен быть добавлен к стартовому набору в едином файле src/types/index.ts.
Код типизации не содержит ошибок линтера и TS.
Объявленные типы и интерфейсы соответствуют тем структурам и данным, которые описаны в документации.
Тип any не используется без необходимости.
Не используется ослабление контроля типов с помощью инлайнового отключения линтера или настроек в tsconfig.json.
Описания одинаковых типов не дублируются. При необходимости используется объединение типов или дженерики.
В классах отдельно объявлен интерфейс для экземпляра и отдельно — для конструктора, если планируется передавать в качестве параметра класс по имени (конструктор).
